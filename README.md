# Filmcase Uploader

اپ اندرویدی فارسی برای آپلود ویدیو از گوشی یا لینک مستقیم به Boxera و دریافت لینک پخش M3U8، به‌همراه مدیریت صف لینک‌ها.

## نسخه 1.5.2
- قرارداد Boxera کلمه‌به‌کلمه با پیاده‌سازی مقایسه شد؛ اختلاف‌های زیر هم در سرور import و هم در اپ اصلاح شدند:
- `part_size` حالا باید داخل پنجرهٔ مجاز باشد: سرور مقدار کمتر از ۵۲۴۲۸۸ یا بیشتر از ۵۳۶۸۷۰۹۱۲۰ را با `422` رد می‌کند، پس `BOXERA_PART_SIZE` نامعتبر **همان لحظهٔ اجرا** و پیش از هر انتقال خطای صریح می‌دهد (نه شکست در میانهٔ آپلود). اگر یک لینک با اندازهٔ پیشنهادی فعلی به بیش از ۱۰۰۰۰ بخش برسد، اندازهٔ بخش خودش بالا می‌رود تا تعداد بخش‌ها زیر سقف بماند.
- `upload_status` فقط `active` یا `completed` است. در حالت `completed` راهنما می‌گوید انتقال را تکرار نکن و برای گرفتن فایل `complete` را تکرار کن؛ قبلاً همین‌جا از `file_id` نشست استفاده می‌شد و `complete` فرستاده نمی‌شد. این هم در سرور import و هم در مسیر آپلود اپ اصلاح شد.
- کلید `upload_request_id` فقط وقتی تکراری می‌ماند که ورودی واقعاً یکی باشد: اگر اندازه، نام یا MIME لینک نسبت به تلاش قبلی عوض شده باشد، کلید تازه‌ای ساخته می‌شود و `file_id` قبلی همراه آن فرستاده می‌شود (همان چیزی که راهنمای resume می‌گوید). قبلاً کلید ذخیره‌شده برای همیشه دوباره استفاده می‌شد و در این حالت `409` می‌گرفت.
- نشستی که در میانهٔ انتقال می‌میرد (`409`) دیگر تسک را شکست‌زده نمی‌کند: یک‌بار نشست تازه با `file_id` قبلی و کلید تازه باز می‌شود و بخش‌هایی که سرور پذیرفته دوباره از لینک خوانده یا ارسال نمی‌شوند.
- کلید ثبت ویدیو از خودِ `file_id` مشتق می‌شود (`video-<hash`)، نه شناسهٔ تسک؛ پس یک فایل جدید کلید تکراری نمی‌گیرد و اجرای دوبارهٔ همان فایل همان ویدیو را برمی‌گرداند.
- شناسه‌های مدیریت عددی‌اند: `file_id` در `uploads/init` و `media_file_id` در `/video/videos` اگر رقم باشند به‌صورت `int` فرستاده می‌شوند، نه رشته (رشتهٔ غیرعددی هم دست‌نخورده می‌ماند تا مقدار ساختگی تولید نشود).
- برای `space=video` نوع MIME همیشه `video/...` است؛ اگر لینک `application/octet-stream` بدهد، نوع از پسوند فایل ساخته می‌شود (mkv → `video/x-matroska` و...). `original_name` و `upload_request_id` به سقف ۲۵۵ و ۱۲۰ کاراکتر کوتاه می‌شوند.
- مسیر آپلود از گوشی هم همان ترمیم‌های نشستی را گرفت: `409` روی `uploads/init` با کلید تازه و همان `file_id` یک‌بار دوباره تلاش می‌شود، و اندازهٔ بخش وقتی فایل به بیش از ۱۰۰۰۰ بخش می‌رسد بزرگ می‌شود.
- آزمون واحد تازه `test/boxera_body_test.dart` بدنهٔ همین دو درخواست را می‌سنجد (بدون شبکه): نوع شناسه‌ها، MIME، کوتاه‌کردن طول‌ها و پنجرهٔ `part_size`.
- آزمون سراسری از ۳۸ به ۶۳ بررسی رسید: `upload_status=completed` (هیچ بایتی دوباره خوانده نمی‌شود)، مرگ نشست در میانهٔ انتقال و ترمیم با نشست تازه، چرخش کلید وقتی ورودی عوض می‌شود، رد `part_size` خارج از مجاز، و سقف ۱۰۰۰۰ بخش. fixtureها هم با قرارداد هم‌خوان شدند: اندازهٔ بخش ۵۲۴۲۸۸ بایت و `upload_status: active`.

## نسخه 1.5.1
- آدرس سرور import را می‌توان بدون `http://` هم نوشت؛ اگر `://` نداشته باشد همان پیشوند اضافه می‌شود، پس `10.0.0.5:8787` مستقیم کار می‌کند.
- اگر یک لینک دوباره به سرور سپرده شود و سرور تسک تازه‌ای بسازد، خطای تلاش قبلی روی کارت می‌ماند و نمایش داده می‌شود؛ حالا رکورد قبلی با رکورد جدید جایگزین می‌شود.
- متن «بدون مصرف اینترنت گوشی» دقیق شد: بایت‌های ویدیو از گوشی عبور نمی‌کند، ولی چند درخواست کوتاه ثبت لینک و پرسیدن وضعیت با دادهٔ خود گوشی فرستاده می‌شود.
- اگر آدرس سرور تنظیم نشده باشد، دکمهٔ سپردن به‌جای بازکردن دیالوگ، مستقیم تنظیمات را باز می‌کند و توضیح می‌دهد.

## نسخه 1.5.0
- بارگذاری لینک از طریق سرور: فایل `tools/boxera-link-importer.mjs` یک سرویس‌دهندهٔ کوچک Node (نسخه ۲۲ به بعد، بدون هیچ وابستگی) است که لینک را **خودش** می‌خواند و تکه‌تکه به Boxera می‌فرستد. این تنها راهی است که فایل روی گوشی ذخیره نمی‌شود و بایت‌های ویدیو از اینترنت گوشی عبور نمی‌کند؛ از دادهٔ گوشی فقط چند درخواست کوتاه ثبت لینک و پرسیدن وضعیت می‌آید.
- اپ هم به همان سرور وصل می‌شود: در تنظیمات «آدرس سرور import» و «توکن سرور import» را وارد کن، بعد در صفحهٔ لینک‌ها دکمهٔ «سپردن لینک‌های فهرست به سرور» یا منوی هر لینک «سپردن به سرور import» را بزن. وضعیت، پیشرفت و لینک M3U8 همان‌جا به‌صورت زنده (هر ۵ ثانیه) تازه می‌شود.
- مقصد‌های قابل انتخاب: فایل در فولدر Drive با `folder_id` (فیلم ۲۷۵۷۶ / سریال ۲۷۵۷۷) یا ویدیوی Boxera در کانال ۴۳. مقصد و شناسه‌ها در تنظیمات ویرایش می‌شوند.
- سرور هر دو پروتکل Boxera را پیاده می‌کند: `s3-multipart` (دریافت `part-urls`، `PUT` روی هر بخش، گزارش ETag با `part-retry` و `complete`) و `tus-edge` (`HEAD` برای آفست، سپس `PATCH`). اگر نشست `upload_status=completed` برگرداند، هیچ بایتی دوباره خوانده نمی‌شود (از 1.5.2 همان‌جا `complete` هم تکرار می‌شود تا شناسهٔ فایل برگردد).
- کارهای ناتمام قابل ادامه هستند: وضعیت هر تسک در فایل JSON ذخیره می‌شود و اجرای دوبارهٔ همان لینک از همان بخش ادامه می‌یابد؛ تا همهٔ بخش‌ها ثبت نشوند `complete` فرستاده نمی‌شود.
- نگهبانی‌های واقعی: لینک باید `Range` و `206` بدهد (وگرنه به‌جای دانلود کامل، خطای صریح برمی‌گرداند)، آدرس‌های loopback/private رد می‌شوند، ریدایرکت‌ها دستی و با همان بررسی دنبال می‌شوند، و بدون `IMPORT_TOKEN` روی آدرس عمومی listen نمی‌کند.
- آزمون سراسری `tools/import_server_selftest.mjs` با یک سرور باکسرای ساختگی و یک سرور لینک Range‌دار، ۳۸ بررسی را انجام می‌دهد (در نسخهٔ 1.5.2 به ۶۳ رسید): بایت‌های بازسازی‌شده باید دقیقاً با فایل مبدأ برابر باشند، `space=drive|video`، `folder_id`/`channel_id`، هر دو پروتکل، رد لینک بدون Range، و API وب سرور. این آزمون در GitHub Actions هم اجرا می‌شود.
- تست‌های واحد `test/import_service_test.dart` برای خواندن JSON سرور، محاسبهٔ پیشرفت از بایت‌ها و حفظ مقادیر شناخته‌شده در تازه‌سازی بعدی وضعیت.
- توکن آپلود Boxera دیگر روی گوشی نمی‌نشیند: همان‌طور که راهنمای Boxera توصیه می‌کند، توکن فقط در متغیر محیطی سرور است. (اپ همچنان می‌تواند مستقیم از گوشی آپلود کند؛ در این حالت توکن در فضای امن Android است و همان ریسک قبلی را دارد.)

## بارگذاری لینک با سرور
باکسرا هیچ نقطهٔ پایانی «این URL را بگیر و خودت دانلود کن» ندارد (راهنمای رسمی `documents?guide=upload-api` فقط `uploads/init`، `part-urls`، `part-retry`، `complete`، `abort` و مسیرهای ویدیو را فهرست می‌کند و مسیرهای حدسی مثل `fetch-url` پاسخ `404` می‌دهند). FTP/SFTP هم فقط راه انتقال فایل است، نه خواندن لینک. پس این اپ یک سرور کوچک برای همین کار می‌سازد.

روی سرور (Node ۲۲+):

```bash
BOXERA_API_TOKEN=توکن-آپلود-باکسرا \
IMPORT_TOKEN=یک-توکن-تصادفی-بلند \
node tools/boxera-link-importer.mjs serve --port=8787 --bind=0.0.0.0
```

آدرس سرور را می‌توانی کوتاه هم بنویسی (مثلاً `10.0.0.5:8787`)؛ اگر `://` نداشته باشد اپ خودش `http://` را اولش می‌گذارد. همهٔ درخواست‌های این اپ از لایهٔ HTTP خودِ Dart می‌روند، پس برای سرور روی شبکهٔ داخلی لازم نیست محدودیت cleartext اندروید را باز کنی؛ با این حال برای سروری که بیرون از شبکهٔ داخلی در دسترس است HTTPS با گواهی معتبر استفاده کن.

مسیرهای HTTP: `POST /import` با بدنهٔ `{"url","kind":"video|drive","folder_id","channel_id","title"}` → `202` و شناسهٔ تسک، `GET /status/{id}` برای وضعیت زنده، `GET /imports` برای فهرست، `GET /health` برای بررسی توکن و صف. همه به‌جز `/health` با `Authorization: Bearer $IMPORT_TOKEN` محافظت می‌شوند.

یک‌بار و بدون سرور هم می‌شود:

```bash
BOXERA_API_TOKEN=... node tools/boxera-link-importer.mjs once \
  'https://cdn.example/film.mkv' --kind=drive --folder-id=27577 \
  --state=/var/tmp/film.json --wait-seconds=1800
```

متغیرهای محیطی: `BOXERA_API_BASE` (پیش‌فرض `https://boxera.ir/api`)، `BOXERA_API_TOKEN`، `BOXERA_PART_SIZE` (پیش‌فرض ۸ مگابایت؛ فقط می‌تواند عددی بین ۵۲۴۲۸۸ و ۵۳۶۸۷۰۹۱۲۰ باشد، وگرنه سرور پیش از هر انتقال با پیام مشخص می‌ایستد. اگر این اندازه یک فایل را به بیش از ۱۰۰۰۰ بخش بیندازد، اندازهٔ بخش به‌طور خودکار بالا می‌رود)، `IMPORT_TOKEN`، `IMPORT_BIND`، `IMPORT_PORT`، `IMPORT_CONCURRENCY`، `IMPORT_STATE_DIR`، و `IMPORT_ALLOW_PRIVATE=1` فقط برای تست روی آدرس‌های داخلی.

## نسخه 1.4.0
- انتقال تکه‌ای لینک به Boxera بدون ذخیرهٔ فایل روی گوشی: با درخواست `Range: bytes=0-0` سنجیده می‌شود که سرور لینک تکه‌خوانی را می‌پذیرد؛ اگر پاسخ `206` و `Content-Range` درست بود، هر بخش آپلود مستقیماً از همان بازهٔ لینک خوانده و با همان `PUT`/`PATCH` به Boxera فرستاده می‌شود. هیچ ویدیویی روی حافظهٔ گوشی نوشته نمی‌شود و فقط یک بخش (پیش‌فرض ۸ مگابایت) لحظه‌ای در حافظه می‌ماند.
- چون Boxera نقطهٔ پایانی برای دریافت مستقیم لینک ندارد، بایت‌ها همچنان از دستگاه کاربر عبور می‌کنند؛ چیزی که حذف شده نوشتن فایل روی حافظه است، نه مسیر شبکه.
- لینک‌هایی که `Range` را نمی‌پذیرند (پاسخ `200` با بدنهٔ کامل) به همان مسیر قبلی می‌روند و در حافظهٔ موقت دانلود می‌شوند؛ در این حالت پیام مشخصی روی کارت کار نمایش داده می‌شود.
- نام، اندازه و MIME از هدرهای همان پاسخ `206` گرفته می‌شود؛ اندازهٔ کل از `Content-Range` خوانده می‌شود، نه از تکهٔ دریافتی.
- پیشرفت هر بخش با دو مرحلهٔ «خواندن از لینک» و «آپلود به Boxera» گزارش می‌شود تا معلوم باشد کدام سفر شبکه در جریان است.
- توقف کار در میانهٔ خواندن یک بخش هم اعمال می‌شود (بررسی لغو بین تکه‌های پاسخ لینک).
- ادامهٔ آپلود نیمه‌کاره برای لینک‌های تکه‌ای هم کار می‌کند: بخش‌هایی که سرور قبلاً پذیرفته از لینک دوباره خوانده نمی‌شوند.
- انتزاع جدید `VideoByteSource` با دو پیاده‌سازی `FileByteSource` و `RangeHttpByteSource`؛ مسیر فایل گوشی و مسیر لینک از همین رابط مشترک تغذیه می‌شوند.
- آزمون واحد برای تحلیل `Content-Range` و خواندن دقیق پنجرهٔ درخواستی از فایل اضافه شد.

## نسخه 1.3.0
- هر عددی که در اپ نمایش داده می‌شود یا اندازه‌گیری واقعی همین دستگاه است یا پاسخ واقعی `/auth/me`؛ فیلد نمایشی یا رزروشده‌ای باقی نمانده است.
- سرعت انتقال و زمان باقی‌ماندهٔ هر کار از نمونه‌های واقعی بایت در یک پنجرهٔ لغزندهٔ ۱۵ ثانیه‌ای محاسبه می‌شود (دانلود لینک، بخش‌های S3 و بخش‌های TUS). وقتی اندازه‌گیری نشده باشد چیزی نشان داده نمی‌شود.
- بخشی که از سرور پذیرفته می‌شود (ادامهٔ آپلود قبلی) انتقال همین اجرا نیست و در عدد سرعت حساب نمی‌شود.
- کارت «حساب Boxera» فقط `user.id`، `can_upload` و `idempotent_init` واقعی پاسخ سرور را به‌همراه زمان بررسی همین اجرا نشان می‌دهد. سهمیه و سقف حجم فایل در این API گزارش نمی‌شود، پس ادعا هم نمی‌شود.
- «دسته‌ها» صراحتاً برچسب محلی‌اند و به Boxera فرستاده نمی‌شوند؛ عنوان «پوشه مقصد» حذف شد.
- هدر صفحهٔ اصلی آدرس API و `channel_id` ذخیره‌شده را نشان می‌دهد؛ برچسب ثابت تزئینی حذف شد.
- پس از بستن اپ، وضعیت اتصال به «در این اجرا بررسی نشده» برمی‌گردد تا نتیجهٔ قدیمی به‌جای وضعیت فعلی نشان داده نشود.
- آزمون واحد برای `TransferMeter` و فرمت سرعت/زمان باقی‌مانده اضافه شد.

## نسخه 1.2.0

- دکمه «افزودن لینک مستقیم» در تب آپلود و «ارسال لینک‌های صف به آپلود Boxera» در تب لینک‌ها.

- نام و نوع MIME فایل از هدرهای `Content-Disposition` و `Content-Type` سرور لینک برداشته می‌شود؛ در نبود آن‌ها از مسیر URL استنتاج می‌گردد.

## امکانات فعلی
- صفحه عیب‌یابی اتصال شامل اعتبارسنجی ساختار URL، DNS، ارتباط HTTPS و پاسخ واقعی `/auth/me`
- تشخیص جداگانه توکن نامعتبر (401)، مجوز ناکافی (403)، مسیر اشتباه (404)، خطاهای سرور، DNS و SSL
- خروجی گزارش عیب‌یابی بدون درج مقدار توکن
- رابط فارسی RTL با تم تیره و رنگ نارنجی
- سپردن لینک به سرور import تا لینک را خودِ سرور بخواند و به Boxera بفرستد؛ فایل روی گوشی ذخیره نمی‌شود و بایت‌های ویدیو از اینترنت گوشی عبور نمی‌کند
- ورود توکن شخصی Boxera از بخش تنظیمات
- ذخیره توکن با Android Secure Storage
- نمایش/مخفی‌کردن و حذف توکن ذخیره‌شده
- بررسی واقعی اعتبار توکن با `GET /auth/me` و نمایش شناسه کاربر، مجوز آپلود و پشتیبانی idempotency
- نمایش سرعت و زمان باقی‌مانده فقط از بایت‌هایی که همین اجرا جابه‌جا کرده است
- افزودن لینک تکی یا گروهی، حذف لینک‌های نامعتبر و تکراری
- انتقال تکه‌ای لینک به Boxera با `Range` بدون نوشتن فایل روی حافظهٔ گوشی (برگشت خودکار به دانلود موقت وقتی لینک Range را نمی‌پذیرد)
- چسباندن لینک از کلیپ‌بورد، ساخت و مدیریت دسته‌های محلی (برچسب روی گوشی، نه پوشه Boxera)
- ذخیره محلی صف و تاریخچه
- بررسی لینک با HTTP HEAD و خواندن Content-Length و Content-Type در صورت پشتیبانی سرور
- گردش‌کار GitHub Actions برای تحلیل، آزمون‌های واحد، آزمون سراسری سرور import و ساخت APK نسخه Release

## مسیر آپلود ویدیو
1. در تب «آپلود» روی «انتخاب ویدیو از گوشی» بزنید و فایل را انتخاب کنید.
2. با «شروع آپلود» نشست ساخته می‌شود: `POST /uploads/init` با `space=video`، نام اصلی، نوع MIME، حجم، `channel_id` و `part_size` (پیش‌فرض ۸ مگابایت؛ فقط وقتی بزرگ می‌شود که فایل با آن اندازه به بیش از ۱۰۰۰۰ بخش برسد). برای هر درخواست یک `upload_request_id` ثابت تولید و ذخیره می‌شود تا تلاش دوباره تکراری ثبت نشود.
3. آدرس بخش‌ها از `POST /uploads/{id}/part-urls` گرفته می‌شود. در `s3-multipart` هر بخش با متد و هدرهای برگشتی مستقیماً روی S3 آپلود می‌شود (بدون توکن Boxera) و ETag آن حفظ و گزارش می‌شود؛ در `tus-edge` آدرس آپلود با `HEAD` همگام‌سازی و سپس با `PATCH` بایت‌ها ارسال می‌شوند.
4. با `POST /uploads/{id}/complete` نشست تکمیل می‌شود و سپس ویدیو با `POST /video/videos` ثبت می‌شود (رایگان، پیش‌فرض `unlisted`، همان `channel_id`).
5. وضعیت با `GET /video/videos/{id}/processing` و فاصله `poll_after_seconds` پایش می‌شود تا `state=ready` یا `failed`.
6. پس از آماده‌شدن، لینک عمومی `m3u8_url` برای کپی نمایش داده می‌شود. `preview_url` مخصوص مالک است، ممکن است منقضی شود و برای مخاطب استفاده نمی‌شود.

> در Boxera، `channel_id` شناسه کانال است و با شناسه حساب فرق دارد. برای ویدیو `folder_id` نفرستید؛ آن مخصوص فایل معمولی است.

## آپلود از لینک
- حالت اصلی، انتقال تکه‌ای است: اپ با `Range: bytes=0-0` می‌سنجد که سرور لینک تکه‌خوانی را می‌پذیرد. اگر پاسخ `206` بود، هر بخش آپلود مستقیماً از همان بازهٔ لینک خوانده و به Boxera فرستاده می‌شود و فایل ویدیویی روی حافظهٔ گوشی نوشته نمی‌شود.
- API باکس‌را مسیری برای دریافت مستقیم فایل از URL روی سرور ندارد (پاسخ‌های probe: `405` برای مسیرهای موجود، `401` برای مسیرهای احراز هویتی و `404` برای هر نام حدسی در ~۵۷ مسیر). به همین دلیل بایت‌ها از دستگاه کاربر عبور می‌کند؛ چیزی که در حالت تکه‌ای حذف می‌شود نوشتن فایل روی حافظه است، نه مسیر شبکه.
- اگر لینک `Range` را نپذیرد (پاسخ `200` با بدنهٔ کامل) یا به لینک دسترسی نباشد، اپ به دانلود موقت در حافظهٔ گوشی برمی‌گردد و پیام «انتقال تکه‌ای ممکن نشد؛ دانلود موقت در حافظهٔ گوشی» روی کارت کار نمایش داده می‌شود.
- لینک باید مستقیم به فایل ویدیویی برسد (mp4، mkv، mov، webm و...). صفحه پخش، لینک نیازمند لاگین و فهرست `m3u8` قابل آپلود نیستند.
- حجم کل از `Content-Range: bytes 0-0/<total>` خوانده می‌شود. در حالت دانلود موقت از `Content-Length` استفاده می‌شود و اگر سرور حجم را اعلام نکند، نوار پیشرفت نامشخص می‌ماند.
- در حالت تکه‌ای، پیشرفت هر بخش با دو مرحلهٔ «خواندن از لینک» و «آپلود به Boxera» گزارش می‌شود؛ بخش‌هایی که سرور قبلاً پذیرفته دوباره از لینک خوانده نمی‌شوند.
- توقف، خواندن بخش جاری را بین تکه‌های پاسخ لینک قطع می‌کند و فایل نیمه‌کاره موقت را پاک می‌کند؛ اگر دانلود موقت کامل شده باشد، فقط آپلود از همان `file_id` ادامه می‌یابد.
- لینک‌های `http://` (بدون SSL) ممکن است توسط اندروید مسدود شوند؛ از لینک `https://` استفاده کنید.
- در حالت تکه‌ای حجم اینترنت همان یک‌بار خواندن به‌علاوه یک‌بار آپلود است و فضایی از حافظهٔ گوشی اشغال نمی‌شود؛ در حالت دانلود موقت، فایل یک‌بار روی حافظه می‌نشیند و پس از آماده‌شدن ویدیو حذف می‌گردد.

## اتصال Boxera
- آدرس پایه پیش‌فرض: `https://boxera.ir/api` (در تنظیمات قابل تغییر)
- احراز هویت با هدر `Authorization: Bearer <upload token>`
- از توکن مخصوص آپلود استفاده کنید، نه توکن ورود پنل.
- اعتبارسنجی توکن از مسیر `GET /auth/me`
- حساب باید مجوز آپلود فعال و سهمیه کافی داشته باشد؛ مجوز از فیلد `can_upload` خوانده و در تب خانه نمایش داده می‌شود.

## امنیت توکن
توکن شخصی در Android Secure Storage دستگاه ذخیره می‌شود و داخل سورس یا GitHub قرار نمی‌گیرد. با این حال، مستندات Boxera توصیه می‌کنند توکن آپلود فقط روی سرور نگهداری شود؛ ذخیره مستقیم در موبایل ریسک استخراج توکن از دستگاه را دارد. این نسخه برای استفاده شخصی محلی در نظر گرفته شده است.

## ساخت APK
با Push یا Pull Request روی شاخه `main`، GitHub Actions پروژه Flutter را آماده، تحلیل و APK نسخه Release را می‌سازد. خروجی از بخش Actions و قسمت Artifacts قابل دریافت است.

برای ساخت نسخه ریلیز، تگ نسخه (مثلاً `v1.5.2`) را Push کنید؛ علاوه بر بیلد، یک GitHub Release با فایل `filmcase-uploader-v1.5.2.apk` ساخته و منتشر می‌شود. APK ریلیز فعلاً با کلید دیباگ امضا می‌شود و برای نصب شخصی مناسب است.

## اجرای محلی
```bash
flutter create --platforms=android --org ir.filmcase .
flutter pub get
flutter run
```

پیش‌نیازهای بیلد اندروید روی سیستم شخصی:
- JDK 17 نصب باشد و `JAVA_HOME` به همان مسیر اشاره کند (JRE 8 کافی نیست).
- Android SDK Build-Tools 36.0.0 و NDK 28.2.13676358 (نسخه پیش‌فرض Flutter) نصب باشند.
- اگر دسترسی به `dl.google.com` برای مخازن Maven محدود است، از میرور (مثل `maven.aliyun.com/repository/google`) در `android/settings.gradle.kts` و `android/build.gradle.kts` استفاده کنید.

اگر فضای دیسک یا ابزار بیلد محلی در دسترس نیست، ساخت APK را به GitHub Actions بسپارید؛ فایل خروجی در Artifacts اجرای Workflow با نام `filmcase-uploader-android` قرار می‌گیرد.
